# 设计思路

> 从「业务现状流程图」（15 环节、3 条人工兜底回路）到「引入 AI 后系统流程图」的映射，
> 以及每一步架构决策背后的取舍。

## 1. 现状问题：三个断点

### 断点一：单据断点
纸质加单与系统单同时到厨房，两套介质之间没有统一的排序依据。
厨师的原话是「得先停下来判断哪张先做、哪道工序不能插队」。
高峰每小时 160 份菜品时，这种判断每单都在发生。

### 断点二：关联断点
套餐拆成菜品后，与原订单的关联丢失。连锁后果：
过敏、温度等备注无法跟着菜品走到工位（**不可逆风险**）；
催菜与加菜事件在日志中混淆，无法追溯。

### 断点三：口径断点
厨房按「出品」算、前厅按「送到桌面」算、顾客按「全部菜齐」算。
三套完成定义各自成立、彼此不可比。后果：催菜靠反复电话，试点结算时才发现指标没法验收。

## 2. 架构决策

### 决策 1：统一业务模型，而不是统一界面
所有来源的订单归一为同一个 `Order` 模型和同一条状态机
（created → parsed → validated → scheduled → cooking → ready → served → closed）。
状态机是「口径统一」的技术载体：只有到达 `served` 才计入已出齐，
`timestamps` 字段记录每个状态的到达时间，出餐时长的分子分母由此唯一确定。

### 决策 2：LLM 只做解析，校验全部确定性
LLM 的位置被严格限制在「自然语言 → 结构化」这一步（`parser.py`）。
菜品存在性、规格合法性、过敏冲突、桌号有效性全部由 `validator.py` 用确定性规则校验。
理由：过敏事件一旦发生无法补救，概率性输出不配承担不可逆风险。

### 决策 3：兜底优先——系统不可用时业务不能停
- 未配置 LLM 或调用失败 → 自动降级规则解析器，置信度打低、转人工复核；
- 解析置信度低于阈值 → 进人工修复队列，**不进自动推荐样本**（数据失真防线）；
- 状态带时间戳与版本号，低置信数据明确标记，不作为实时承诺。

### 决策 4：写操作闸门——建议、确认、留痕
Agent（厨师长/系统）可以产出改派、换菜等**建议**（`Suggestion`），
但生效必须经 `confirm_suggestion()` 人工确认，确认后写入审计日志。
系统放在「建议者」的位置，把最终决定权留给现场的人——
这也是案例门店「不自动决定过敏替代方案」边界的工程化表达。

### 决策 5：事件驱动而非对象互调
五个角色 Agent 之间不直接调用方法，全部通过 `EventBus` 发布/订阅事件
（`EventType` 共 19 种）。好处：责任边界与流程图的人工回路一一对应，
任何一环缺席时事件挂起（如过敏单未签核则停在 validated），而不是悄悄跳过。

### 决策 6：排序可解释，不用模型黑箱
排菜引擎（`scheduler.py`）用确定性加权：过敏 P0（+100）> 催菜（+40）>
外卖时限（+10）> 等待时长（+2/分钟）+ 工序链关键路径。
每个任务输出 `reasons` 列表，厨师长看到的不是「系统说了算」，而是「为什么它排在前面」。

## 3. 角色与责任边界

| 角色 | 系统内职责 | 引入 AI 后的变化 |
|---|---|---|
| 点品员 OrderClerkAgent | 接单、归一、解析、校验 | 从「传话催菜」变为「试图容错解答」 |
| 食安主管 FoodSafetyAgent | 过敏行签核，未签核不得排菜 | 从「事后核实」变为「前置签核」 |
| 厨师长 ChefSupervisorAgent | 确认排菜、确认改派、处置异常 | 从「判断先后」变为「审核协议 + 签发」 |
| 档口厨师 StationChefAgent | 开工/完工上报、缺料一键标记 | 确认接单、标记完成，动作被计量 |
| 传菜 RunnerAgent | 核对桌号、上桌回写 | 核对系统状态而非核对菜名 |

七类强制转人工（本原型实现其中三类）：未知菜品、过敏冲突、缺料/异常。
其余（停机处理、知识库无返回、误写争议仲裁、宾客投诉）在 roadmap 中。

## 4. 口径定义（验收依据）

| 指标 | 分子 | 分母 | 排除规则 | 统计周期 |
|---|---|---|---|---|
| 出餐时长 | served 时间戳 − created 时间戳 | 已上桌订单 | 作废单、异常挂起超 30 分钟的单 | 班次 |
| 漏菜 | closed 时 status ∉ {served, void} 的行 | 已结账订单 | 顾客主动退菜（void 有留痕） | 班次 |
| 催菜 | URGE 事件计数 | — | 同单 5 分钟内去重 | 班次 |
| 过敏传递率 | 签核通过的过敏单 | 全部过敏单 | — | 硬性门槛 100%，不达标不予验收 |

## 5. 已知取舍与未做

- **进程内事件总线**：单店试点够用；多门店需要换成消息队列。
- **工序建模是线性链**：未建模蒸锅/灶眼等资源占用冲突（二期「高级约束求解」）。
- **无持久化**：审计日志 JSONL 追加写，订单状态在内存；生产需接入数据库。
- **LLM 解析未做流式与重试**：失败直接降级，宁可慢一点转人工，不做半吊子结果。
