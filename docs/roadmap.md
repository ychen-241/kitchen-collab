# 路线图

> 本文档由项目报价单（一期分项 + 二期可选功能）**脱敏**而来：只保留功能边界与依赖关系，
> 不含价格与商务条款。

## 一期：后厨出品协同最小闭环 ✅（本仓库已实现的部分）

| # | 分项 | 原型实现位置 | 状态 |
|---|---|---|---|
| 1 | 系统单接入与补录单入口 | `parser.py`（POS/扫码/外卖/电话·纸质五源） | ✅ 原型级 |
| 2 | 订单归一与撞单差异提示 | `parser.normalize_orders` | ✅ 原型级 |
| 3 | 出品排序引擎 | `scheduler.py`（约束 + 可解释理由） | ✅ 原型级 |
| 4 | KDS 三端呈现与超时提醒 | `scheduler.StationBoard`（档口/打荷/传菜数据源） | ⚠️ 仅有数据层，无屏端 UI |
| 5 | 异常识别与一键标记 | `EventType.SHORTAGE / URGE / RETURN_DISH` | ✅ 语音标记未实现 |
| 6 | 过敏原合规链路（P0） | `validator` BLOCK + `food_safety_sign` 签核 | ✅ 核心已实现 |
| 7 | 人工兜底与操作审计 | `Suggestion` 闸门 + `AuditLog` JSONL | ✅ 三类转人工已实现 |
| 8 | 基线埋点与指标看板 | `audit.Metrics`（口径见 design.md §4） | ✅ CLI 看板 |

**一期验收口径**（与报价单一致，去除价格）：
1. 过敏备注传递完整率 100%（含套餐拆单场景）—— 硬性门槛，不设整改期
2. 出餐时长 28 → 22 分钟以内（阶段性目标）
3. 漏菜 14 次/晚 → 6 次以内（阶段性目标）
4. 催菜查询次数下降 30% 以上（阶段性目标）

## 二期可选功能（依赖一期沉淀的订单与工艺数据，建议一期稳定运行 3 个月后评估）

| # | 分项 | 内容 | 原型现状 |
|---|---|---|---|
| 1 | 多模态接单 | 语音/拍照下单转结构化、行业词纠错、置信度阈值 | LLM 文本解析已留好接口 |
| 2 | 知识库与 RAG | 菜品工艺卡、过敏原库、历史决策检索与溯源 | `menu.MenuBook.search` 是最小版 |
| 3 | 高级约束求解 | 蒸锅/灶眼占用建模、多档口负载均衡、二次重排 | `rebalance` 是简化版 |
| 4 | 桌台联动与上菜核对 | 上菜状态回写、错上/缺菜核对 | `serve_order` 单点已通 |
| 5 | 结账归零与数据沉淀 | 账单同步、单店闭环归零、经验资产化 | 状态机 closed 已定义 |

## 工程化待办（原型 → 试点的差距）

- [ ] 订单与任务持久化（SQLite 起步）
- [ ] KDS Web 端（档口/打荷/传菜三屏）
- [ ] 语音播报与一键标记（离线可用）
- [ ] 断网降级：只读快照 + 重连按业务编号去重补齐
- [ ] POS 中间件（现有 POS 无接口时约 4 人天工作量）
- [ ] 七类强制转人工补全（停机处理、知识库无返回、仲裁、宾客投诉）

## 明确不做（价值边界）

- 不自动决定过敏替代方案
- 不做静默改序/改派/退菜
- 不在低置信数据上做自动推荐
- 不过敏原库的「判断」——系统只传递与留痕，准确性由门店食安负责人负责
